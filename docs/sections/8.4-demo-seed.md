### Role switcher (dogfood/dev only)

| Layer | Flag | Default |
|-------|------|---------|
| SPA chrome | `VITE_ROLE_SWITCHER=1` or Vite `import.meta.env.DEV` | hidden in production build without flag |
| API route | `ROLE_SWITCHER_ENABLED=1` or `createAppWithAuth` (e2e) | **off** in `createAppFromBindings` unless env set |

`POST /api/auth/dev/role-switch` body: `{ role, eventId? }` → session cookie for seeded demo user + `{ ok, role, email, eventId, redirectTo }`.  
Zod validated; E4 envelopes on 400/401/403/404; audit `Auth.DevRoleSwitch` with `correlationId` (never logs tokens).

**Auth gate (production dogfood):** when `bootstrapPolicy` is `controlled` (Worker default), the route requires an **existing valid session cookie** before minting a demo role session. A workers.dev hostname is not private by itself — unauthenticated callers cannot obtain event-admin access by discovering the endpoint. Local e2e (`createAppWithAuth` / open bootstrap) may allow unauthenticated switch for harness convenience.

Does **not** weaken cookie flags, CSP, or scope checks for demo convenience.
